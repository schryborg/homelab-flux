# AGENTS.md

Guidelines for AI agents working on this repository.

## Repository Overview

This repository contains a [Flux CD](https://fluxcd.io/) GitOps configuration for a single k3s homelab cluster.

- **Cluster name:** `homelab`
- **Flux version:** `v2.9.6`
- **Git source:** `ssh://git@192.168.50.22/luke/flux.git` (branch `main`)
- **Bootstrap path:** `./clusters/homelab`
- **Target namespace:** `flux-system`

Flux is bootstrapped into the k3s cluster and reconciles manifests from this repository automatically.

`clusters/homelab/kustomization.yaml` includes the Flux bootstrap resources and the cluster-level Flux Kustomizations for infrastructure and apps. `clusters/homelab/infrastructure.yaml` defines three Flux `Kustomization` resources: `infra-controllers` points to `./infrastructure/controllers`; `infra-configs` points to `./infrastructure/configs` with `dependsOn: infra-controllers` so configuration is applied only after the controllers are ready; and `databases` points to `./infrastructure/databases` with `dependsOn: infra-controllers` so database clusters are provisioned only after their controlling operators are ready. `clusters/homelab/apps.yaml` points to `./apps`. Component-level `flux-kustomizations.yaml` files may define further Flux Kustomizations for distinct reconciliation paths (for example, a Helm release and its dependent ingress).

`gotk-components.yaml` is generated by `flux bootstrap` and should not be hand-edited. Manual edits will be overwritten on the next bootstrap/upgrade.

## Conventions

- One cluster per directory under `clusters/<name>/`.
- Cluster-wide infrastructure lives under `infrastructure/`; applications live under `apps/`.
- Database clusters and database-backed services live under `infrastructure/databases/<controller>/<app>/`, where `<controller>` is the operator/controller that provisions them (e.g., `cnpg`) and `<app>` is the consuming workload or service (e.g., `infisical`).
- Keep top-level Kustomize entrypoints updated when adding or removing components (`apps/kustomization.yaml`, `infrastructure/controllers/kustomization.yaml`, `infrastructure/configs/kustomization.yaml`, and `infrastructure/databases/kustomization.yaml`).
- Components that need separate Flux reconciliation paths should define Flux `Kustomization` resources in their `flux-kustomizations.yaml` and include that file from the component's Kustomize entrypoint.
- Keep Helm sources/releases together under a component's `helm/` directory; keep related configuration or ingress resources in their own subdirectories when separately reconciled.
- Use `dependsOn` when one Flux Kustomization must wait for another, such as applying MetalLB configuration after installation or ingress after an application release.
- Keep sensitive values out of plain YAML; use `SealedSecrets`, `SOPS`, or external secret references.
- Use resource names and namespaces consistently; namespace is usually declared explicitly in manifests, with a `namespace.yaml` file in the database component directory when the database needs its own namespace.

## Common Operations

These commands assume `flux` CLI and `kubectl` are configured for the homelab k3s cluster.

```bash
# Reconcile the entire flux-system configuration
flux reconcile kustomization flux-system --with-source

# Check Flux status
flux status
flux get all

# Suspend / resume a kustomization
flux suspend kustomization <name>
flux resume kustomization <name>

# Preview the bootstrapped cluster entrypoint or infrastructure paths
kubectl kustomize ./clusters/homelab
kubectl kustomize ./infrastructure/controllers
kubectl kustomize ./infrastructure/configs
kubectl kustomize ./infrastructure/databases
```

### CloudNativePG database credentials

When a CNPG `Cluster` is bootstrapped with `initdb.owner`, the operator creates
credentials secrets automatically. For a cluster named `<cluster>` in namespace
`<namespace>`:

- Application owner secret: `<cluster>-app` (user is the `owner` value)
- Superuser secret: `<cluster>-superuser` (if default superuser access is enabled)

Retrieve the owner password (e.g., for `infisical-db` in `infisical`):

```bash
kubectl get secret -n infisical infisical-db-app -o jsonpath='{.data.password}' | base64 -d
```

To use this in a workload, reference the secret directly instead of copying the
value out. For example, in an environment variable:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: infisical-db-app
        key: password
```

## Safety Rules

1. **Never commit raw secrets.** Use sealed secrets, SOPS, or external secret stores.
2. **Do not hand-edit `gotk-components.yaml`.** Use `flux bootstrap` or `flux install` to update Flux.
3. **Validate manifests before committing.** If `kustomize` is available, run `kubectl kustomize --load-restrictor=LoadRestrictionsNone <path>` to ensure resources build cleanly.
4. **Be careful with `prune: true`.** Removing a manifest from Git will delete it from the cluster on the next reconciliation.
5. **Keep parent Kustomize entrypoints and Flux reconciliation paths in sync when adding or removing components.**

## Adding Infrastructure

1. Decide whether the component is a controller/operator, cluster-wide configuration, or a database cluster provisioned by a controller.
2. Add controller components under `infrastructure/controllers/<name>/` with a `kustomization.yaml`. Add config components as `infrastructure/configs/<name>.yaml` (or under `infrastructure/configs/<name>/` if multiple files are needed) and include them in `infrastructure/configs/kustomization.yaml`. Add database clusters under `infrastructure/databases/<controller>/<app>/` with a `kustomization.yaml` and register the `<controller>` directory in `infrastructure/databases/kustomization.yaml`.
3. Register controllers in `infrastructure/controllers/kustomization.yaml`, configs in `infrastructure/configs/kustomization.yaml`, and database controller groups in `infrastructure/databases/kustomization.yaml`.
4. If a config or database depends on a controller, ensure the dependency is expressed with `dependsOn` (e.g., `infra-configs` and `databases` already depend on `infra-controllers`; add component-level `dependsOn` for finer-grained ordering when needed).
5. Validate with `kubectl kustomize ./infrastructure/controllers`, `kubectl kustomize ./infrastructure/configs`, `kubectl kustomize ./infrastructure/databases`, and any affected subdirectories.
6. Commit and run `flux reconcile kustomization flux-system --with-source` to verify.

## Adding Applications

1. Add the application under `apps/<name>/` with a Kustomize entrypoint.
2. Include it in `apps/kustomization.yaml`.
3. Use component-level Flux Kustomizations to reconcile its manifests; separate Helm resources and dependent resources (such as ingress) when they require distinct ordering or reconciliation paths.
4. Validate the parent entrypoint and all relevant manifest directories with `kubectl kustomize`.

## Known Issues / TODO

- **Infisical database shares the application namespace.** The CNPG cluster for Infisical currently lives in the `infisical` namespace alongside the application, rather than in a dedicated `infisical-db` namespace as the repository convention prefers. This is a workaround because the `infisical-standalone` Helm chart references the database connection URI via `secretKeyRef`, and Kubernetes does not allow pods to read Secrets from another namespace. Once a cross-namespace secret mechanism such as External Secrets Operator or SealedSecrets is available in the cluster, the database should be moved back to its own namespace.
